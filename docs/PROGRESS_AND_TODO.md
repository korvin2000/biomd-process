## GOAL:
"Цель: спроектировать и начать реализацию модульного, расширяемого и user-friendly приложения для пакетной обработки custom bio.md Markdown-документов через LLM.
Основные режимы (один из 2 или оба одновременно):

1. Metadata extraction: эвристически извлекать заданные метаданные и сохранять их в заданном JSON-формате по конфигурируемому шаблону пути/имени.
2. Translation: качественно переводить bio.md на конфигурируемый список языков, максимально точно сохраняя структуру и Markdown-разметку; сохранять результат по шаблонному пути/имени.

Сначала разработай архитектурный план и общий каркас приложения. Первая версия должна быть не полной реализацией для обработки bio.md-специфики и заданных выходных форматов, а надежной абстрактной платформой для LLM batch-processing: domain-specific parsing, validation и output logic можно оформить через interfaces/adapters/wrappers с TODO для следующих этапов.
Требования:

* TypeScript + Node.js; используй подходящие зрелые библиотеки/готовые решения, если они действительно упрощают систему.
* Четкая модульная архитектура, небольшие компоненты/классы/функции, понятные зависимости и extension points. Следуй KISS, SOLID, DRY, clean code и разумному OOP; не переусложняй и не создавай god-classes.

## Hashcode-подход — и для JSON, и для markdown

Модель больше не видит ни JSON, ни markdown. Она получает плоскую таблицу `{contentHash: text}` и возвращает `{contentHash: перевод}`; документ пересобирается локально подстановкой.

Из markdown не отправляются: `#`, маркеры списков, `:::`-контейнеры, их `src:`/`position:`/`size:`, код в фенсах, все URL. `caption:` — отправляется, это отображаемый текст. URL внутри предложения маскируются как `⟦1⟧`, чтобы переводчик видел целую фразу; каждая маска проверяется на выживание перед приёмом ответа.

Замерено на `examples/ru`:

| | payload против файла | дедупликация |
|---|---|---|
| дословье (`localize`) | **−52%** | 142 → 117 строк (**−18%**) |
| статья (`translate`) | **−18%** (9–26% по файлам) | между разными статьями ~0 |

По markdown экономия скромнее, чем звучит идея — я сначала написал в конфиге «больше половины», замерил и исправил на фактические 18%. Но главный выигрыш там не в байтах: **структура не может сломаться, потому что её не отправляли**, и `dates`/`ranking`/`url`/`target` идентичны во всех изданиях по построению, а не по инструкции модели. Значит, ни один retry и ни одна эскалация на дорогую модель не тратятся на починку разметки. Ключ — это хеш содержимого, поэтому одинаковая строка (`Гитарист` в каждом дословье) переводится один раз за прогон.

Режим `document` остался: `tasks.translate.mode: document`, когда важнее максимум контекста.

# Session 3 — the duplicate translation call, and closing out `TODO(domain)`

## Отправная точка: два одинаковых вызова перевода

Прогон `20260814-145008-0eac`, журнал:

```
seq 8   llm.attempt   attempt 1  outcome=error  "missing translation for 1 key(s): f81e8af3"
seq 9   llm.retry     attempt 1  delayMs=225
seq 10  llm.attempt   attempt 2  outcome=success
```

`f81e8af3` — абзац `==Для тестового каталога== …`. Модель вернула 19 ключей из
20, валидатор отверг **всю** таблицу, и все 20 фрагментов ушли и были оплачены
второй раз. Это не дублирующая отправка, а **гранулярность retry**: система
умела чинить только целый батч.

Замечание в ту же сторону из того же прогона: из 6332 output-токенов **4950 —
reasoning**. `reasoning.enabled: false` означало «не отправлять параметр», а не
«не рассуждать», так что модель, рассуждающая по умолчанию, была неостановима.

## Что сделано

**1. Repair вместо повтора батча** (`stringBatch.ts`). Первый вызов принимает
частичный ответ; недостающие и повреждённые ключи переспрашиваются отдельно.
Последний раунд — строгий, поэтому не закрытая дыра всё ещё становится обычной
validation failure и наследует retry → fallback на модель посильнее, но уже на
payload из нескольких ключей. Ответ, непригодный целиком (не JSON, не объект),
лестницу пропускает. `repairAttempts: 0` возвращает прежнее поведение — ручка
покрывает старое поведение, а не только новое.

Плюс: фрагмент без единой буквы (`1893–1987`, одинокий `⟦1⟧`) не отправляется
вообще. Это и токены, и одна из типичных причин, по которым модель роняет ключ.

**2. Reasoning стал управляемым.** `dialect: none` (новый дефолт) — не слать
ничего; любой другой диалект формулирует намерение в обе стороны, и
`enabled: false` — это инструкция «не рассуждай». В summary появилась доля
reasoning в output-токенах, чтобы причина дорогого прогона была видна сразу.

превратить прототип в production-ready producer этого формата.

## 1. `src/domain` — формат реализован ровно один раз

Новый слой, зависящий только от `shared`. Всё, что знает, что такое каталог,
живёт здесь; `core`, `routing`, `reliability`, `state` о гитаристах не знают.
Изменение спецификации имеет ровно одну точку приземления.

`types.ts` (документы и порядок членов) · `values.ts` (домены `VD-*`) ·
`countries.ts` (249 alpha-2 + alpha-3 + названия на десяти языках через
`Intl.DisplayNames` + демонимы) · `vocabulary.ts` (`type`/`gender`/doctype/`lang`
из синонимов на любом языке корпуса) · `dossier.ts` (санитизация с миграцией
v1→v2, слияние без перезаписи, домашний порядок членов) · `catalog.ts`
(`CatalogIndex`, `mergeNameIndex`) · `validate.ts` (`INV-1 … INV-28`).

Два свойства кода, из которых следует остальное:

- **Узко на выходе, широко на входе.** Каждый нормализатор выдаёт ровно
  каноническую форму и принимает любое правдоподобное её написание.
  Переписать `1893-02-21` бесплатно; переспросить — круглый рейс, который
  чаще всего вернёт `1893-02-21` снова.
- **Отбрасывать, а не угадывать.** `external/07` §7.2 правило 5. Все поля досье
  опциональны: отсутствующая строка корректна, неверная — утверждение о человеке.

**Изменение поведения:** частичные даты (`1885`, `05.1885`) больше не
сохраняются — спецификация их не представляет, и они отбрасываются. Плюс
проверка календаря: `31.02.1900` не пишется.

## 2. Плоский контракт извлечения — главная экономия

Было: JSON Schema досье в system-промпте (**1923 tok**) **и та же схема** в
`response_format` (**1195 tok**) — на каждом вызове каждого документа. Это учило
модель структуре, которой у неё нет и не должно быть.

Стало: плоская карточка из ~22 коротких ключей (**660 tok**) и
`response_format: json_object` (**7 tok**). Досье собирается локально
(`FlatFields.buildDossier`).

**≈ 2450 входных токенов на документ**, до всего остального. Плюс исчез целый
класс ошибок формы: вложенность, массив вместо comma-list, запрещённые члены,
формат даты, написание enum'а — теперь это не то, что модель может испортить.

Парсер терпим намеренно: принимает плоский объект, вложенный ответ
(`{metadata:{…}}`) и строки `key: value`. Каждая из трёх форм — это retry,
которого не будет.

## 3. Чего у модели больше не спрашивают вовсе

- **Галерея.** `media.photos` / `media.music` — это подпись и путь, и статья
  содержит и то и другое: `::: image` контейнеры и таблицы табулатур.
  `documents/markdown/media.ts` их разбирает. Ноль токенов, и `target` —
  тот путь, который в статье, а не тот, который модель перепечатала.
  (Попутно: `\r\n` ломал все `$`-якорные шаблоны атрибутов — тихо и только на
  Windows.)
- **`ranking`.** Редакционная оценка проекта не является фактом статьи. Убран из
  карточки по умолчанию, остаётся доступен через `tasks.extract.fields`.
- **Всё об entry, у которой уже есть досье.** `onExistingDossier: reuse`
  (по умолчанию) — ноль вызовов; `complete` — только недостающие ключи;
  `rebuild` — с нуля.

Существующим считается **только** файл рядом со статьёй. Собственный выход
extract'а намеренно не входит в его план: прогон, увидевший файл, который сам же
и написал, менял бы fingerprint и перепланировался бы вечно. На вопрос «выход уже
актуален?» отвечают `--resume` и `run.skipExistingOutputs`.

## 4. Каталог обновляется, а не пересобирается

Пересборка `index.json` из того, что попало в текущий прогон, — самое
разрушительное, что producer может сделать с этим форматом: прогон по
подмножеству удалил бы все непосещённые строки вместе с их `id`, а поломка
join'а к `index-<lang>.json` **молчалива** — имена просто откатываются к
латинскому `title`.

`CatalogIndex.load` читает существующий файл, `upsert` правит его на месте:
переживают порядок строк, неизвестные члены, ручная классификация и все `id`.
`mergeNameIndex` — то же для файлов имён: авторский `[0]` не заменяется,
дописываются только новые алиасы. Издание объявляется, только если на диске есть
**и** статья, **и** досье (`INV-8`); язык, который прогон не проверял, не
трогается.

## 5. `biomd validate`

`INV-1 … INV-28` над опубликованными файлами. Без модели, без сети. Почти все
поломки этого формата молчаливы во время работы, поэтому корректность нужно
**проверять**, а не намереваться.

Проверка дубликатов ключей JSON делается по сырому тексту: парсер оставляет
последнее вхождение, и информация теряется до того, как её кто-либо увидит.

На вендоренных `examples/root-index` валидатор сразу нашёл реальный дефект:
`index-ru.json` содержит ключи 11–15, которых нет в `index.json`.

## 6. Найдено по дороге

Идиома `<%_ … _%>` во **всех** шаблонах склеивала строки: `_%>` съедает перевод
строки после тега. Списки и условные строки в промптах выводились слипшимися.
Исправлено на `<% if (…) { %>содержимое\n<% } %>`. Отдельная ловушка: тег,
начинающийся с `(`, — синтаксическая ошибка, потому что ASI не срабатывает после
`tR+="…"` перед открывающей скобкой.

## Проверено

264 теста (было 167), typecheck и build зелёные. Новые файлы: `domain.test.ts`,
`media.test.ts`, `validate.test.ts`; переписаны `extraction.test.ts`,
`catalog.test.ts`, расширен `run.e2e.test.ts`.

Удалены как перекрытые: `MetadataContract.ts`, `normalize.ts`, `merge.ts`,
`IdAllocator.ts`, зависимость `zod-to-json-schema`. Закрыт последний
`TODO(domain)` про `schemaFile` — внешняя JSON Schema больше не нужна, потому что
схемы в промпте больше нет.

## Что осталось

- Footnote ids в скелете — когда в корпусе появятся сноски.
- `documents[]` не harvest'ится из статьи: ссылка на документ и ссылка на другую
  запись синтаксически неразличимы, а неверный документ хуже отсутствующего.
- Алиасы для CJK: алгоритмического пути от 塞戈维亚 к «Segovia» нет, работает
  только подсказка модели. Это ограничение формата, не реализации.
- `INV-15` (согласие `index-<lang>[id][0]` с `forename + surname`) валидатором не
  проверяется: исключений (`INV-16` — roster, общие досье) больше, чем сигнала.

# v0.3 — портрет, веб-поиск, частичные даты

Три задачи, поставленные вместе, потому что все три про одно: **статья — не
единственный источник фактов**, а формат не должен выбрасывать то, что известно
не полностью.

## 1. Частичные даты (`catalogue.datePrecision`)

`external/02` требует опускать дату, известную не до дня. На реальном корпусе это
означает потерю факта каждый раз, когда в статье написано «родился в 1885 году».

Решение: понизить порог настройкой, а не переписывать спецификацию. Публикуемая
форма — каноническая `DD.MM.YYYY`, **усечённая слева**: `02.1893`, `1893`.
`day` возвращает поведение спецификации в точности.

Почему это безопасно, и почему это записано ровно в одном месте (комментарий у
настройки): VD-DATE обязывает консьюмера считать значение вне
`\d{1,2}\.\d{1,2}\.\d{4}` **отсутствующим**. Строгий читатель игнорирует `"1893"`
и ведёт себя ровно так же, как если бы поле выбросили. Ничего не ломается.

Побочные решения:

- `normalizeDate(raw, minPrecision)` стал заметно шире на входе: ISO, точки,
  слэши, `1893-02`, `05.1885`, названия месяцев на семи языках корпуса
  («21 февраля 1893», «21 de marzo de 1893»), квалификаторы приблизительности
  (`c.`, `ок.`) — год остаётся, оговорка отбрасывается. Диапазоны (`1885–1890`)
  отбрасываются: названы две даты, и ни одна из них не *эта*.
- `mergeDossier` получил **единственную перезапись во всём коде**: `refinesDate`.
  `1893` и `21.02.1893` — не два конкурирующих факта, а один факт, известный на
  двух глубинах; отказ от уточнения оставлял бы заглушку навсегда.
- Валидатор принимает то, что разрешает настройка, и **не** предупреждает на
  каждое частичное значение: настройка и есть заявление о намерении, а
  предупреждение на каждой строке сделало бы `--strict` неприменимым.

## 2. `portrait` — выбор фотографии (`src/images`)

Вход — `images/artists.json` (2059 записей) и `images/image-index-spec.md`.
Спецификация описывает разумный конвейер; данные ему не соответствуют, и
расхождение определило почти весь дизайн:

| Спецификация | Реальные данные |
|---|---|
| `meta.people` — сильнейший сигнал (100) | пусто во **всех** 2059 записях |
| `meta.title`, `ocr` | пусто во всех |
| `meta.description` (40) | XMP-дамп Lightroom в 72 записях |
| `meta.keywords` (55) | EXIF-рациональные (`"282/100"`) в 10 записях |
| `nameTokens` / `nameTokensRu` (90) | единственный работающий сигнал |

Отсюда — guard на мусорные `meta.*` и опора на путь. В пути обнаружилось больше,
чем описано в спецификации:

- **Буква каталога.** `photo/<L>/` — инициал того, под кем файл заведён (1586 из
  1974 совпадений по первому токену). `photo/b/buek_segovia.jpg` — фотография
  Буэка, на которой есть Сеговия: прекрасный снимок и неверный аватар. Штраф
  −0.30, и это самая полезная эвристика из всех.
- **Директория-персона против директории-дискографии.** `almeida_laurindo/4lalm07.jpg`
  (в имени файла нет ничего) и `paco_de_lucia/siroco.jpg` (обложки альбомов) —
  одна и та же форма. Поэтому совпадение по директории слабее, чем по имени файла,
  а необъяснённое собственное имя в имени файла штрафуется.
- **Маркеры релизов.** `pena_cd05_1993.jpg` — конверт диска, который
  классифицируется как `portrait`, одно лицо, высокая уверенность. Исключаются по
  умолчанию. Ловушка: `\b` перед `_cd` не срабатывает никогда — `_` это `\w`.
- **`nameTokensRu` — варианты написания, а не люди** (`сеговия|сеговиа|зеговия`).
  Пока это не было учтено, каждая русская запись теряла 0.2 на «второго
  человека», и Сеговия не находился вовсе.
- **Контекст досье.** `segovia_linares.jpg` — Линарес это место рождения, а не
  вторая фамилия. Слова из `birthplace`/`bands`/`instruments` исключаются из
  проверки на «второго человека».

Ранжирование — лексикографический ключ §14, а не взвешенная сумма, с двумя
огрублениями, каждое из которых исправляло реальную ошибку выбора:

- **identity полосами по 0.1.** Выше порога все кандидаты — нужный человек;
  разница 0.03 между «в имени файла полное имя» и «только фамилия» не повод
  публиковать худшую фотографию.
- **`faceCoverage` перед гибридным счётом.** §14 существует именно чтобы
  мегапиксели не перевешивали лицо; единый счёт возвращает эту проблему —
  цветной снимок 0.15 MP с лицом на 1% кадра обыгрывал ч/б, где человека видно.

Порог `minIdentity: 0.9` применяется **к identity, а не к сумме** (§16): красивый
портрет чужого человека — не кандидат. Ниже порога `img` не пишется вовсе —
`external/03` §3.4.9 уже описывает подстановку по гендеру, и синтетические
заглушки намеренно не попадают в галерею, в отличие от значения, записанного в
`img`.

Чего сознательно **не** делаем: различение однофамильцев. `photo/w/john_williams/`
не разрешается анализом имён никак, а эвристика, которая «догадается», ошибётся
молча. Ответ там — курируемый `img` в `index.json`, который пайплайн никогда не
перезаписывает.

Отладка порогов вынесена в `biomd portrait "Андрес Сеговия" --top 10`: ничего не
тратит, показывает весь ранжированный список с причинами. Прогон по 17 реальным
именам — 16 попаданий, один отказ (Бобри: все его снимки tier 3).

## 3. `websearch`

Мотив прямой: `extract`, эскалирующий контекст ради факта, которого в документе
нет, платит трижды за одно и то же молчание. Задача берётся ровно с этой точки —
и спрашивает **другой источник**.

Всё в ней условно: вопросы вычисляются из досье (`gaps.ts`), нет пробелов — нет
запроса, нет артефакта, нет стоимости. Статья не отправляется никогда: по проводу
идёт карточка из ~8 коротких строк плюс, опционально, лид-абзац с ограничением по
длине — исключительно чтобы отличить однофамильца.

Правило живости: возраст ≥ `livenessAgeYears` (78) при пустом `died` превращает
отсутствие в вопрос — биография, написанная при жизни, о смерти не скажет никогда.
Контракт ответа — `status: alive | dead | unknown`, и дата смерти пишется
**только** при явном `dead`. Молчание о живом человеке не должно становиться
датой; `filterLiveness` выбрасывает дату, пришедшую без статуса.

Приёмка ответа отказывает чаще, чем принимает: доменная нормализация каждого
значения, обязательный URL-источник, порог уверенности, отказ от «уточнения»,
противоречащего записанному. Маршрутизация требует capability `web_search` —
модель без поиска ответит на эти вопросы всё равно, бегло и без источника, и
именно это ограничение и предотвращает.

307 тестов (было 275), typecheck и build зелёные. Новые файлы: `portrait.test.ts`,

## Что осталось

- Однофамильцы (см. выше) — ограничение данных, не реализации.
- LLM-арбитраж между близкими кандидатами на портрет: спроектирован (передавать
  таблицу метаданных, не изображения — файлов локально нет), не реализован, потому

- `upgradePrecision: false` по умолчанию: уточнять год до дня через веб-поиск
  дороже, чем полезнее, пока корпус не будет полным.
