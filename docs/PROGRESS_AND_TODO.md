# Session context, progress, TODO's

## GOAL:
"Цель: спроектировать и начать реализацию модульного, расширяемого и user-friendly приложения для пакетной обработки custom bio.md Markdown-документов через LLM.
Основные режимы (один из 2 или оба одновременно):

1. Metadata extraction: эвристически извлекать заданные метаданные и сохранять их в заданном JSON-формате по конфигурируемому шаблону пути/имени.
2. Translation: качественно переводить bio.md на конфигурируемый список языков, максимально точно сохраняя структуру и Markdown-разметку; сохранять результат по шаблонному пути/имени.

Сначала разработай архитектурный план и общий каркас приложения. Первая версия должна быть не полной реализацией для обработки bio.md-специфики и заданных выходных форматов, а надежной абстрактной платформой для LLM batch-processing: domain-specific parsing, validation и output logic можно оформить через interfaces/adapters/wrappers с TODO для следующих этапов.
Требования:

* TypeScript + Node.js; используй подходящие зрелые библиотеки/готовые решения, если они действительно упрощают систему.
* Четкая модульная архитектура, небольшие компоненты/классы/функции, понятные зависимости и extension points. Следуй KISS, SOLID, DRY, clean code и разумному OOP; не переусложняй и не создавай god-classes.
* Конфигурация должна быть простой для обычного использования, но расширяемой. System/user prompts каждого типа задач храни в отдельных template-файлах, чтобы их можно было независимо менять, версионировать и тестировать.
* Поддержка одной или нескольких LLM через OpenAI-compatible endpoints. Для каждой модели/endpoint должны настраиваться model, reasoning/reasoning effort и другие релевантные параметры.
* Нужен отдельный scheduler/router для распределения задач между LLM. Предусмотри несколько встроенных стратегий в духе OmniRoute: cost-optimized, context-optimized, sequential/fallback switching, а также простой интерфейс для добавления собственных стратегий.
* Поддержка локальных proxy/gateway (LiteLLM, OmniRoute, 9router и аналоги) и удаленных API вроде OpenRouter.
* LLM-вызовы должны быть reliable: timeouts, классификация ошибок, retries с backoff/jitter, retry только когда это безопасно, fallback на другой endpoint/model, контроль лимитов и отсутствие бесконечных повторов.
* Система должна быть cost/token optimized. Минимизируй повторную и лишнюю передачу контекста, проектируй стабильные cache-friendly prompts/prefixes и учитывай prompt caching. Стратегия обработки длинных документов должна быть настраиваемой: full document, truncation-first, chunking, staged extraction и другие разумные способы сначала получить результат на меньшем контексте, переходя к более дорогой обработке только при необходимости.
* Workflow должен быть resumable и пригодным для batch-processing: не перерабатывать успешно завершенные элементы без необходимости, уметь продолжать работу после сбоя.
* Нужны прогресс и наблюдаемость: количество файлов/задач, LLM requests, retries/fallbacks, errors, token usage и по возможности cost. Вести machine-readable JSON/JSONL protocol/state для восстановления и анализа выполнения.
* Нужен простой практичный интерфейс первой версии (CLI/TUI или другой минимальный вариант), показывающий прогресс и ошибки без построения тяжелого UI.

Разделяй:

2. LLM providers/endpoints;
3. routing/scheduling;
4. task pipelines;
5. prompt/template management;
6. input/output adapters;
7. retry/fallback/reliability;

Не трать много времени на конкретные правила bio.md, schema extraction или детали перевода — оставь для них расширяемые контракты и TODO. ## Что сделано

**План архитектуры** — [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md): слои, направление зависимостей, модель данных, путь LLM-вызова, точки расширения, явный список того, что намеренно не доделано.

**Работающий скелет** — 85 модулей TypeScript/ESM (~7000 строк), разложенных ровно по девяти запрошенным зонам:

| Зона | Модуль | Ключевое |
|---|---|---|
| configuration | `src/config` | YAML + Zod, слои `defaults < file < ${ENV} < CLI`, cross-field проверки, редактирование секретов |
| LLM providers | `src/llm` | один OpenAI-compatible транспорт покрывает LiteLLM/OmniRoute/9router/vLLM/OpenRouter/OpenAI; reasoning через 3 диалекта; usage, cached-tokens, cost |
| routing | `src/routing` | `cost-optimized`, `context-optimized`, `sequential`, `round-robin`, `least-failures` + `defineStrategy` для своих |
| reliability | `src/reliability` | таксономия ошибок → retry (тот же таргет) и fallback (следующий) как **две независимые оси**, backoff+jitter, `Retry-After`, circuit breaker, rate limiter |
| task pipelines | `src/pipelines` | `extract` и `translate` поверх общего escalation-движка |
| prompts | `src/prompts` + `prompts/` | шаблоны в файлах, версионируются хешем, `MessageBuilder` гарантирует «стабильное — первым, документ — последним» |
| input/output | `src/io` | glob-discovery, path-шаблоны с санитизацией, атомарная запись |
| state/logging | `src/state`, `src/observability` | `run.json` + `events.jsonl` + `state.json`, метрики, structured logger |
| core | `src/core` | `JobPlanner` (планирование отделено от исполнения) и `Orchestrator` (p-queue, бюджет, failFast, SIGINT) |

**Экономия токенов** устроена так: prompt-cache префикс байт-в-байт одинаков на всём корпусе; context-стратегии эскалируют от дешёвого к дорогому (`head` → `full` → `chunked`); resume по fingerprint делает повторный прогон неизменённого корпуса бесплатным.

## Мои дефолты (выбраны без вопроса, меняются в конфиге)

- Один work item = один документ; `translate` порождает по задаче на язык, поэтому упавший немецкий не переделывает английский.
- Fingerprint включает контент, промпты и output-контракт, но **не** модель — добавление fallback-модели не должно переделывать корпус.
- Перевод игнорирует глобальную `truncation-first` и использует `chunked`: усечённый перевод бессмысленен.
- Токенайзер — эвристика с поправкой на кириллицу/CJK, а не tiktoken (точный подсчёт между провайдерами всё равно невозможен, интерфейс подменяемый).
- Убрал `tasks.*.maxAttempts` из конфига — retry/fallback/эскалация уже покрывают это, а неиспользуемая ручка хуже её отсутствия.

## Hashcode-подход — и для JSON, и для markdown

Модель больше не видит ни JSON, ни markdown. Она получает плоскую таблицу `{contentHash: text}` и возвращает `{contentHash: перевод}`; документ пересобирается локально подстановкой.

Из markdown не отправляются: `#`, маркеры списков, `:::`-контейнеры, их `src:`/`position:`/`size:`, код в фенсах, все URL. `caption:` — отправляется, это отображаемый текст. URL внутри предложения маскируются как `⟦1⟧`, чтобы переводчик видел целую фразу; каждая маска проверяется на выживание перед приёмом ответа.

Замерено на `examples/ru`:

| | payload против файла | дедупликация |
|---|---|---|
| дословье (`localize`) | **−52%** | 142 → 117 строк (**−18%**) |
| статья (`translate`) | **−18%** (9–26% по файлам) | между разными статьями ~0 |

По markdown экономия скромнее, чем звучит идея — я сначала написал в конфиге «больше половины», замерил и исправил на фактические 18%. Но главный выигрыш там не в байтах: **структура не может сломаться, потому что её не отправляли**, и `dates`/`ranking`/`url`/`target` идентичны во всех изданиях по построению, а не по инструкции модели. Значит, ни один retry и ни одна эскалация на дорогую модель не тратятся на починку разметки. Ключ — это хеш содержимого, поэтому одинаковая строка (`Гитарист` в каждом дословье) переводится один раз за прогон.

Режим `document` остался: `tasks.translate.mode: document`, когда важнее максимум контекста.
